## 0. TL;DR

A free, open-data snow forecasting site for western US ski areas: NBM point forecasts for every ski area with probabilities, snow level and snow ratio, **model plumes** (HRRR, RRFS, GFS, ECMWF HRES + ENS, AIFS experimental, GEFS), SNOTEL observations, avalanche context, NWS alerts and public verification.

**Priority now:** code-review safety and data-loss fixes (`docs/BACKLOG.md` MR 1–4) → scope trim, with plume sampling decoupled from map rendering first (MR 6) → platform Phase 0–1 (`platform-transition.md` §10) = W1 hosting → W2 pages → W4 PWA → NBM + plume UI passes → W6 alerts. Details in §8.2.

**Hard rules for all code**
1. Safety info (avalanche danger, NWS alerts, snow level/rain-at-base, data freshness) is never gated or hidden.
2. Never present a heuristic as an accuracy claim or an avalanche rating. Label heuristics.
3. Open, license-clean data only; keep attribution (§10.2) on pages and charts.
4. One accumulation period per chart axis; **never sum, scale or interpolate percentiles across windows** (ranges come from one native NBM window); uncertainty shown by default as **p25–p75 ("likely", the middle half of NBM's outcomes) for snowfall, snow level and snow ratio**; 10–90% only where explicitly noted (DESIGN §6); sources + issue times on every module.
5. Sources fail independently; fetch separate from pure functions; offline tests with fakes.
6. Stay within static-host limits (20,000 files/deploy, 25 MiB/file) — bulk data goes to R2.

## 7. Architecture notes

- Pipeline modules: `catalog.py`, `nbm/`, `points.py`, `summary.py` (§5.7), `ecmwf.py`, `gefs.py`, `models/multimodel.py` + `ridge.py` (plume and ridge-wind sampling), `snotel.py`, `alerts.py`, `avalanche.py`, `archive.py`, `verify.py`, `pages.py` (§5.10), `alerts_backend.py` (§5.11). Rules: fetch separate from pure functions; offline tests with fakes; sources fail independently.
- **Today:** GitHub Actions (`update-site`, `models`, `ecmwf`, `gefs`, `verify`, `tests`) publish product tars on the `model-maps` release; the hourly build unpacks them and deploys to GitHub Pages. GitHub delivers few scheduled runs here; the external scheduler (`infra/scheduler/`) is built, not deployed (fix review M14 and M10 first).
- **Target:** one Docker image runs every `python -m pipeline <cmd>` on Cloudflare Containers, started by Cron Triggers → Workflows; outputs go to R2 (atomic: staging prefix, then pointer); catalog, latest summaries and run health in D1; a WX API Worker serves web, mobile and agent (`platform-transition.md` §2–§6). Blockers listed in BACKLOG ("Blocks: MOVE").
- **Pipeline health:** a failed or stale run notifies the on-call developer and the public status page shows last success per source.
- Size budget: points ≈ 160 ski areas × ≤ 150 KB (+ SNOTEL-site forecast files kept for verification) in R2, not in the site bundle.
